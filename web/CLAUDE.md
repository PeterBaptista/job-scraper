## Commands

All commands run from `web/`:

```bash
pnpm dev             # Dev server on http://localhost:3000
pnpm build           # Production build
pnpm lint            # ESLint

pnpm db:generate     # Generate migration from schema changes
pnpm db:migrate      # Apply pending migrations
pnpm db:studio       # Drizzle Studio (DB browser)
```

## Architecture

### Auth

Better Auth with email + password. `proxy.ts` (Next.js 16 replacement for `middleware.ts`) reads the session cookie and redirects unauthenticated requests to `/login`. Public routes: `/login`, `/signup`, `/api/auth/**`.

Server-side session: call `requireSession()` from `lib/auth/get-session.ts` in API routes — it throws `'Unauthorized'` if no session, which route handlers catch and convert to 401.

### Data flow

```
POST /api/scraping
  → writes scraping_job row (status: queued) to DB
  → publishes {id, user_id, source} to RabbitMQ queue scrape_jobs

scraper service updates scraping_job progress in DB

GET /api/scraping/:id → reads scraping_job from DB → frontend polls every 2s
```

### Key layers

| Layer | Location | Role |
|---|---|---|
| Auth | `lib/auth/` | Better Auth server + client + `requireSession()` helper |
| Schema | `lib/db/schema.ts` | Single source of truth for all table definitions |
| Repository | `lib/repositories/job.repository.ts` | All DB queries, always scoped to `userId` |
| Services | `lib/services/` | Business logic; thin wrappers over repository |
| Queue | `lib/queue/message-queue.ts` | Publishes to RabbitMQ; reads `scraping_job` status from DB |
| API routes | `app/api/` | Call `requireSession()`, delegate to services, return JSON |
| Features | `features/` | Co-located components, hooks, and API fetch functions per domain |

### Database schema (lib/db/schema.ts)

Better Auth tables: `user`, `session`, `account`, `verification`

App tables:
- `job` — scraped listings, always queried with `userId` filter
- `scraping_job` — real-time progress updated by the scraper service
- `scraping_session` — completed scraping history

### Migrations

After any change to `lib/db/schema.ts`:
```bash
pnpm db:generate   # creates a new SQL file in lib/db/migrations/
pnpm db:migrate    # applies it
```

Never edit migration files after they have been applied to any environment.

### Frontend

- `app/page.tsx` → `<DashboardContent>` (client component)
- `features/jobs/` and `features/scraping/` — co-located hooks, API clients, components
- TanStack Query for all data fetching; `staleTime: 60s`, `refetchOnWindowFocus: false`
- `useScrapingStatus` polls every 2s while a job is active; on completion invalidates the jobs query via `useEffect`
- UI: shadcn/ui primitives (Radix + Tailwind CSS v4) in `components/ui/`

### Supported values

```ts
JobSource = 'linkedin' | 'glassdoor' | 'indeed' | 'other'
JobStatus = 'new' | 'viewed' | 'applied' | 'interviewing' | 'rejected' | 'offer'
ScrapingJobStatus = 'queued' | 'processing' | 'completed' | 'failed'
```

### Resume editor (`/jobs/[id]/resume`)

The tailored CV is edited here rather than delivered by Telegram. The PDF is
generated by ReportLab in the scraper from a structured content dict, so the form
edits *that dict* — there is no editable document underneath.

This is the only feature that calls the scraper over HTTP. The browser never
reaches port 8000: `lib/services/resume.service.ts` checks job ownership against
`jobRepository` and then proxies through `lib/services/scraper.client.ts`, so
Better Auth stays the single auth boundary. `SCRAPER_URL` and `SCRAPER_TOKEN` must
be set, the token matching `INTERNAL_API_TOKEN` in `scraper/.env`.

Things that look like bugs but are not:

- **The score can disagree with the form.** It describes the rendered PDF. One-page
  fitting drops bullets at tier 4, and the scraper replays those drops before
  scoring, so `preview.ats` reflects less content than was typed. The dropped
  bullets are listed in the preview pane.
- **`indeterminate` renders no number at all.** An empty job description is unknown
  fit, not a score of zero.
- **Truthfulness violations block commit but not download.** The file is the user's
  own; feeding an automated application is where an unbacked claim does damage.
- **Autosave (`PUT`) and commit (`POST /commit`) are different things.** Only commit
  writes a real PDF and repoints `job.resume_path`, which is what Easy Apply
  uploads. Until then the "não salvo para candidatura" badge means the worker would
  still send the previous document.
